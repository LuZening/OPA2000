========================================================================
  A. 阻塞项（不改就不工作）
========================================================================

------------------------------------------------------------------------
【A1】★★★ PF5 = PTT_INX 现在是单上升沿，踩下踏板进不了中断 ★★★
------------------------------------------------------------------------
当前 ioc：
    PF5.GPIOParameters=GPIO_PuPd,GPIO_Label
    PF5.GPIO_Label=PTT_INX
    PF5.GPIO_PuPd=GPIO_PULLUP
    PF5.Signal=GPXTI5
  注意：这一行**没有** GPIO_ModeDefaultEXTI，CubeMX 默认给
  External Interrupt Mode with **RISING** edge only。

  而 PTT_INX 是低电平有效：
      踩下 = 下降沿 → 现在不触发 → 功放起不了射
      松开 = 上升沿 → 现在触发   → 只收到"松开"

要改成：
    [ ] GPIO Mode 选 **External Interrupt Mode with Rising / Falling
        edge trigger detection**（生成的 main.c 里应变成
        GPIO_MODE_IT_RISING_FALLING）

代码侧已就绪：PTT ISR 读的是引脚实时电平，不区分哪个边沿，双边沿不会算错；
松开的兜底轮询在 TIM7 tick 里，最多一个 tick 内也会对齐。

------------------------------------------------------------------------
【A2】★★★ NVIC 里根本没有 EXTI9_5_IRQn —— 只改 A1 也没用 ★★★
------------------------------------------------------------------------
当前 ioc：NVIC 列表里**没有** NVIC.EXTI9_5_IRQn 这一行。
  EXTI5（PF5）属于 EXTI line[9:5] 组，NVIC 不开这一组，
  就算边沿改成双边沿，中断也不会被 CPU 响应。

要加：
    [ ] NVIC → 勾 **EXTI line[9:5] interrupts**
        抢占优先级 **1**，子优先级 0

  这是最容易漏的一条。A1 和 A2 必须同时做。

------------------------------------------------------------------------
【A3】NVIC 里也没有 EXTI2_IRQn（GT911 触摸 INT，PF2）
------------------------------------------------------------------------
当前 ioc：
    PF2.Signal=GPXTI2      （GT911 的 LCT_INT）
  但 NVIC 里没有 NVIC.EXTI2_IRQn。

  [ ] 可选：勾 **EXTI line[2] interrupts**，抢占优先级 5

  说明：我查过 touch.c，touch_process() 是**轮询读触摸**的，
  不依赖这个 INT 标志，所以不开也不影响触摸使用。
  只有将来想用 INT 做低功耗唤醒时才需要开。优先级低，可以先跳过。

  B. 建议项（不改能跑，但打得折扣 / 有风险）
========================================================================

------------------------------------------------------------------------
【B1】TIM5_IRQn / TIM7_IRQn 抢占优先级 2 → 1
------------------------------------------------------------------------
当前 ioc：
    NVIC.TIM5_IRQn=true\:2\:0\:...
    NVIC.TIM7_IRQn=true\:2\:0\:...
  代码假设这两者应在 FreeRTOS 之上、硬件保护之下，即抢占优先级 1：
    TIM5 = 继电器 15ms 延时 one-shot
    TIM7 = 快速 tick（PTT 释放兜底 + 蜂鸣器音阶 + 风扇测速）

  [ ] TIM5_IRQn 抢占优先级 2 → **1**
  [ ] TIM7_IRQn 抢占优先级 2 → **1**

  不改的后果：不致命。只是这两个 tick 可能被同优先级的 DMA/SPI 中断
  拖延，PTT 释放兜底响应和风扇测速精度会略降。

------------------------------------------------------------------------
【B2】AWD 门限初值（代码会覆写，但上电瞬间有影响）
------------------------------------------------------------------------

    ADC1.AWD1HighThreshold=32767
    ADC1.AWD2HighThreshold=32767
    ADC2.AWD1HighThreshold=32767
  （LowThreshold 未设 = 0）

  代码 adc_calibration.c 会在运行时用 adc_awd_set_*() 直接写
  ADC1->HTR1/2/3、LTR1/2/3，所以 ioc 初值只影响"上电到第一次配置
  之间"这一小段。建议顺手改成：
    [ ] ADC1.AWD1HighThreshold = 0        （等波段配置写满再启用，避免误触发）

  ⚠ STM32H7B0 上 AWD1/AWD2/AWD3 各有独立 LTR1/HTR1、LTR2/HTR2、
    LTR3/HTR3，互不干扰（与 H743 不同），可放心分别设限。

  背景：架构改为「内部 128KB FLASH 只放 bootloader，app 的代码/只读数据/
  字库全部放在外部 OSPI（memory-mapped 0x90000000）里 XIP 运行」。

------------------------------------------------------------------------
【E1】★★★ 禁用 OCTOSPI1 —— 否则 app 一上电就 HardFault ★★★
------------------------------------------------------------------------
  当前 ioc：
      Mcu.IP20=OCTOSPI1
      VP_OCTOSPI1_VS_quad.Mode=quad_mode
      PF6..PF10 / PG6 复用为 OCTOSPIM_P1
  → CubeMX 会在 Core/Src/main.c 里生成并调用 MX_OCTOSPI1_Init()。

  问题：app 的取指就跑在 OCTOSPI1 的 memory-mapped 映射里。MX_OCTOSPI1_Init()
  一旦执行 HAL_OSPI_Init() 去写 OSPI 寄存器，映射当场失效 → 下一条取指即崩。
  参考工程 LLMC_DAC 的 app main() 里**没有** MX_OCTOSPI1_Init 调用，OSPI 完全
  交给 bootloader；本工程必须同样处理。

  为什么我不直接改 main.c：它由 CubeMX 生成，重新 Generate 会恢复调用；
  正确的永久做法是在 ioc 里禁用该外设。

  [x] 已改。本 Agent 已核对生成代码：
        · Core/Src/main.c 中已无 MX_OCTOSPI1_Init() 调用
        · Core/Src/octospi.c 已不在 cmake 编译列表内
      （磁盘上残留的 octospi.c/octospi.h 会在下次 Generate 时被 CubeMX 删除）

------------------------------------------------------------------------
【E2】★★★ MPU：OSPI 必须可缓存 + 允许取指；SRAM 划出不可缓存窗口 ★★★
------------------------------------------------------------------------
  你已在 ioc 里重设 MPU（生成代码 Region0..Region6）。本 Agent 按 app.ld 的
  实际内存布局逐条核对，结论：**R4 和 R6 两处必须再改，其余已经正确**。

  已正确：
    R0  0x08000000  256KB   内部 FLASH（app 不用，保留无妨）
    R1  0x90000000  128MB   CACHEABLE + INSTRUCTION_ACCESS_ENABLE   ← OSPI/XIP
    R2  0x20000000  128KB   NOT_CACHEABLE（DTCM；TCM 本就不走 cache，无妨）
    R3  0x24000000  1MB     CACHEABLE                              ← AXI SRAM
    R5  0x30000000  128KB   CACHEABLE（D2 SRAM1，本工程未用）

  ✗ (1) R4 = 0x24000000 / 512KB / AccessPermission = **NO_ACCESS**  ← 致命
        它比 R3 编号高，会盖住 0x24000000-0x24080000；而 app.ld 恰好把
        .framebuffer(0x24000000) 和 .dma_no_cache(0x24040000，装了 ADC/CAT/
        USB/ALC/LVGL 的全部 DMA 缓冲) 放在这一段。NO_ACCESS 会让 CPU 一碰
        就 MemManage fault（第一次 LCD 刷新 / USB 发送即挂）。
      → AccessPermission 改成 **FULL_ACCESS**；IsCacheable/IsBufferable 保持
        NOT_CACHEABLE/NOT_BUFFERABLE（这正是要的“不可缓存窗口”）。
        DisableExec 保持 DISABLE 即可（纯数据窗口）。

  ✗ (2) R6 = 0x38000000 / 32KB **继承了 R5 的 CACHEABLE**  ← 需改
        这是 D3 域 SRAM4；app.ld 的 .d3_dma_buffer 把 LPUART1 的 BDMA2 接收
        缓冲放在 0x38000000。BDMA 直接写内存、不维护 cache，若该区可缓存，
        CPU 读到的会是陈旧数据。
      → IsCacheable = **NOT_CACHEABLE**、IsBufferable = **NOT_BUFFERABLE**；
        AccessPermission 保持 FULL_ACCESS。

  背景（为什么 R1/R4/R6 是这三种属性）：
    · 外部 OSPI（R1）必须 cacheable+可执行，否则 XIP 取指又慢又可能被 exec
      位拦住；见 ST 对 H7 的说明：D3 只能被 D3 主线访问，TCM 只有 MDMA 能到。
    · AXI SRAM（R3）默认 cacheable；只有 DMA 会碰的 framebuffer/DMA 窗口
      （R4 = 0x24000000 起 512KB）单独挖成不可缓存。
    · D3 SRAM4（R6）是 BDMA2 唯一能访问的存储，必须不可缓存。
  ⚠ R4/R6 的基址与大小必须和 app.ld 对齐（地址由 app.ld 导出的
    _framebuffer_start / _dma_no_cache_start / _d3_dma_buffer_start 固定，
    不会漂移）：
        .framebuffer    0x24000000  256KB
        .dma_no_cache   0x24040000  ~56KB（R4 的 512KB 窗口内）
        .d3_dma_buffer  0x38000000  256B

  [ ] 改 R4、R6 两处 + 重新 Generate Code。
  [ ] 生成后确认 Core/Src/main.c 的 MPU_Config() 里 R4 是 FULL_ACCESS +
      NOT_CACHEABLE、R6 是 NOT_CACHEABLE。

      默认 config），无需手动改 .ioc，Generate Code 后保持。
    - 引脚：I2C2_SCL = PF1 / I2C2_SDA = PF0（hw_pinmap.h 已定义）。但 .ioc
      不会自动把 PF0/PF1 配成 I2C2 AF——你需要打开 CubeMX 找到 I2C2 那个
      外设，在 "I2C" 模式下把 PF0/PF1 设为 AF4。
    - 完成后 Generate Code，PF0/PF1 的 AF 复用就会被 main.c 启动；STM32
      上电后 NS2009 probe 即可在 100 ms 内 ACK 成功。

  app 工程侧完全独立于这个 ioc 改动：即使暂时没启用 I2C2 AF，arm 端编
  译仍能过（hi2c2 不存在会链接错，但 CMSIS 引导会卡；建议在你做完
  ioc 之前不要烧录）。

  ioc 改完后，自检流程：
    1. main() 里 touch_init() 输出"NS2009" / "GT911" / "SPI-XPT2046"——
       建议加到 touch.c 的 s_resistive_kind 判断后用一个 fprintf
       / printf 到 ITM（如果没接 SWO 看不到，可以省）。
    2. 启动后若 g_calibration_required 跳到校准界面：5 点校准，点完后
       config_save 写入 g_config.touch.* + calibrated=1，下次启动
       应直接到主屏。
    3. 若 config_init 返回 false（首启 / 抹掉 config），校准自动
       弹。
    4. 若想强制重做校准：菜单 → Settings → 触屏校准（或短按 PF4 /
       拔 config 一次）。当前 gui.c 里 gui_show_calibration() 仍
       可手动调。
